# Delta-only release (--flash)

Agent-chat modifier, not an executable or .NET CLI option. Accept it on `release full|inhouse|production`, `prepare inhouse|production` and `pipeline inhouse|production`; normalize `full --flash`, `inhouse --flash`, `production --flash` to the `release` commands. The bare flag may precede or follow the command words. Reject valued/duplicate flags, unknown options and --flash on indexing/promote/bootstrap before writes; `--silent` combines per release-notify.md. Without --flash, existing command semantics are unchanged. Quoted examples authorize nothing.

## Scope override

Flash is for a routine release that finishes in about five active minutes when nothing needs a decision. It keeps the command expansion and owner/publication boundaries of release-steps.md but replaces I with the delta review below; with prepare/pipeline it narrows the stale-index prerequisite and V/D review to that delta, and pipeline never bumps. H/P reconcile only delta changelog/notes. This explicit mode replaces this package's full Backfill, historical catalog and README capability inventory for this invocation; it does not mark project-wide indexing complete, rewrite target instructions or override higher-priority restrictions.

Read this file, release-timing.md, release-notify.md for Production, the target AGENTS.md and only §2.3, §5.2, §6, §7 and §8.2 of the target AGENTS.release.md. Open release-steps.md, release-tools.md or other sections only for a recovery, a real conflict, a missing or incompatible tool, or a bootstrap install.

## Fast path

1. Start the timer, then run `agm-workspace.mjs release preflight` once. It fetches and reports branch and owner pairs, latest tag, dirty paths, finished work branches (M), `autoActions`, `questions` and `blockers`; do not repeat them command by command. Check bootstrap freshness from its receipt; apply a compatible update now or not at all.
2. Perform preflight `resolve` steps yourself (merge, resolve conflicts, test, commit) without asking. The command is the confirmation (release-workflow.md Command authority and anomaly confirmation): the only possible question is a version anomaly, asked here together with preflight `questions`, or a later candidate anomaly. Blockers stop only the affected publication.
3. `release sync plan/apply` (merge `origin/develop`, back-merge `jenkins`/`jenkins-release`) and `integrate gather plan/apply` for this release's own branch only.
4. Tools: reuse `.agrimap-agent/runtime/release-tools.json` if at most 7 days old with the same agm-release version in `dotnet tool list -g`; otherwise follow release-tools.md once and rewrite it.
5. Baseline per environment comes from the preflight owner values and the matching verified tag or checkpoint; never pick the largest tag or reuse a Production tag as Inhouse history. Review baseline-to-candidate committed changes plus dirty paths, reading changed content and affected dependencies only.
6. Prepare once: explicit owner target, otherwise owner PATCH+1. Full prepares both; Production-only leaves Inhouse unchanged; Inhouse writes no Production notes/index/tag. Update the changelog for this delta and Production release.md/notes when selected; keep historical text.
7. Uncommitted edits the run did not write are this release's pending work: group their diff by topic and commit each group (`feature|fix|comment:`, Thai, written from the diff) before the version commit; `deliver plan` adopts them. Leave a path local only on the owner's explicit exclusion, a secret, ignored/runtime state or a nested repository. Unpushed local commits (merged work on develop, run-owned or earlier) are part of the candidate: push them in D, never an anomaly or a reason to stop. A failing or incompatible gate never ends a flash run blocked: ask the release-tools.md numbered-option question once and continue on the answer. A free-text answer (`ทำต่อ`, `continue`, cause fixed) retries the failed step once, then takes the publishing option; never repeat the question, even on resume.
8. Safe-tier sweep of the delta (sonarqube-remediation.md), one `fix:` commit. Verify owner pairs and allowed diffs, secrets, notes completeness, `git diff --check` and tag collision. `git diff --check` skips exported/generated paths verified elsewhere (db-schema exports, generated clients, `.gitattributes -whitespace`): never reformat or block on them. A delta with no feature/fix entry gets the changelog line `maintenance only` and continues. Reuse test/build evidence while content, build context, dependencies and tools match; when they changed, build now instead of stopping; flash is not skip-tests. A local Docker build is optional (Jenkins Build builds the image): an unavailable engine or storage records `Docker: not verified locally` and continues to D unasked; only a failure on a working engine asks once. `SECRET_SUSPECTED` is a question (its card), never a blocked run: finish independent steps, then ask.
9. D: commit content (`feature|fix|comment:`, Thai description) and version (`bump:`) separately, run `release sync plan/apply` again, push develop once; a rejected push syncs and retries at most twice unasked. J: fast-forward and push jenkins. Q/C: show version, SHA and tag as one progress line and continue (ask only for a candidate anomaly). T: fast-forward jenkins-release, create and push the annotated tag from the notes blob.
10. F: one final local `audit:` commit, no develop push (it ships with the next D push) and no intermediate audit commits; N for Production. Before D, report merged work as `local only, not pushed`. End with command, versions, branch/tag results, verification reused/run, excluded work and the mandatory release-timing.md output block.

## Avoid repeated overhead

Write records with a file tool or script, never shell `echo`/here-strings. Batch independent read-only checks, serialize Git mutations and check every exit code. On an uncertain push outcome inspect remote refs before retrying; a tag failure resumes only the tag checkpoint. Never forward --flash to the .NET CLI, force-push, move tags or edit CI triggers. No guaranteed duration or green-deployment claim; single push per ref applies.
