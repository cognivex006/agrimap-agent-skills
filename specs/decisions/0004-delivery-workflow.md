# 0004 — Delivery workflow ที่ชั่งน้ำหนักตามความเสี่ยง และทำงานร่วมกับ subagent

- สถานะ: อนุมัติแล้ว (owner decision 2026-11-05, บันทึกใน 6.0.1)
- ผู้ตัดสินใจ: owner ของ agrimap-agent-skills
- ขอบเขต: ทุก agm-* operation ที่ทำงาน durable ใน product project และเอกสาร runtime `references/delivery-workflow.md`, `references/subagents-and-branches.md`, `references/lifecycle-core.md`

## บริบท

ข้อสรุปมาจากการคุยกับ owner 6 คำถามต่อเนื่อง (2026-11-05):

1. SDLC เดิมยังใช้ได้ในยุค AI ไหม แต่ละขั้นหมายถึงอะไร
2. ถ้าออกแบบ lifecycle ใหม่ให้เหมาะกับ agent จะเป็นแบบไหน
3. lifecycle ต้องชั่งน้ำหนักได้ทั้งงานเล็ก กลาง ใหญ่ ไม่ใช้ดาบเล่มใหญ่ทุกงาน แต่ความสามารถและความครบถ้วนต้องไม่ตก
4. workflow ที่ใช้ได้จริง ไม่ใช่แค่ทฤษฎี
5. workflow ครบเส้นตั้งแต่วางแผนจนหลังขึ้น production
6. flow ที่มี subagent ร่วมทำงาน

หลักฐานจากงานเดียวกัน (5.0.17): กฎ nested ternary มีตั้งแต่ 5.0.12 แต่เกิดซ้ำ เพราะกฎอยู่ในไฟล์ที่ agent เปิดเฉพาะตอนแก้ scan; fix ตามคำแนะนำของ CA1862 กลับตรรกะ; test code หลุดมาตรฐาน; session อื่นสลับ branch ใน folder เดียวกันกลางงาน

ของที่มีอยู่แล้วและยังใช้ต่อ: depth `light / standard / regulated` ใน lifecycle-core (เดิมเลือกตามความต้องการบันทึกและ assurance), orchestration decision, contract-first, หนึ่ง writer ต่อไฟล์, ไม่เกิน 5 agent, rolling queue และ worktree ชั่วคราวใน `%TEMP%` ที่ Leader รวมกลับแล้วลบ (subagents-and-branches.md, 5.0.1/5.0.10)

## การตัดสินใจ

1. **คัดแยกด้วยความเสี่ยง ไม่ใช่ขนาด.** งาน durable ทุกงานเริ่มด้วย 4 คำถาม (contract/security/DB/production/ของที่ publish แล้ว, ข้าม lane หรือมีผู้เรียกนอกไฟล์, มี test คลุมไหม, รู้ไหมว่าเสร็จคืออะไร) แล้วประกาศ depth พร้อมเหตุผลหนึ่งบรรทัดก่อนลงมือ depth เท่ากับสัญญาณที่หนักที่สุด ไม่ใช่ค่าเฉลี่ย
2. **depth กำหนดทั้งการบันทึกและการตรวจ.** ระดับเบาตัดพิธี (เอกสาร การอนุมัติ ขอบเขตการตรวจ) แต่ไม่ตัดความถูกต้อง
3. **Invariant floor ทุกระดับ:** อ่าน state จริง, โหลดกฎของภาษาที่เขียน, self-gate (รวม test code), รันการตรวจที่ถูกที่สุดที่พิสูจน์การเปลี่ยนได้, รายงานแยกตรวจแล้ว/ยังไม่ได้ตรวจ, ไม่ทำสิ่งที่ย้อนกลับไม่ได้โดยไม่มีสิทธิ์
4. **ยกระดับกลางทางแบบประกาศ.** เจอสัญญาณใหม่ให้หยุด ประกาศระดับใหม่พร้อมเหตุผล แล้วทำขั้นของระดับใหม่ให้ครบ การยกเป็น regulated ต้องรอคนตอบ การลดระดับต้องมีหลักฐาน
5. **Workflow ครบเส้น A–O** ตั้งแต่รับโจทย์ คัดแยก กลั่นโจทย์ วิเคราะห์ วางแผน เตรียม branch ลงมือ ตรวจรวม PR integrate Inhouse UAT Production ติดตามหลังปล่อย และเรียนรู้ แต่ละ depth เดินเฉพาะขั้นที่ต้องการ
6. **คนอยู่เฉพาะจุดตัดสินใจ:** เคาะ contract, เลือกแนวทาง (regulated), ดูสรุป PR เมื่อพฤติกรรมเปลี่ยน, ตรวจรับเมื่อผู้ใช้เห็นผล, อนุมัติ Production และทุกสิ่งที่ย้อนกลับไม่ได้
7. **Subagent มีบทบาทชัด:** Explorer และ Analyst อ่านอย่างเดียว, Worker เขียนเฉพาะไฟล์ใน brief, Verifier ตรวจโดยไม่ใช่คนเขียน; Leader คนเดียวคุยกับคน commit/merge/release light ไม่ใช้ subagent
8. **Worktree (owner 2026-11-05):** หลายคนหรือหลาย agent เขียนพร้อมกันใช้ worktree ได้ปกติ; คนเดียวหรือ writer เดียวทำบน work branch หลัก เงื่อนไขเดียวคือหลังจบงานต้องรวมทุกอย่างกลับให้ครบ (ตรงกับกฎ worktree เดิมของ 5.0.10 ที่ยังใช้ต่อ)
9. **Brief และการตรวจผลของ subagent:** brief 8 ข้อ, Leader ตรวจขอบเขตไฟล์/ผลตรวจจริง/self-gate/สัญญาเองเสมอ, แก้ซ้ำโดย subagent ได้ 1 รอบแล้ว Leader รับกลับ
10. **วงเรียนรู้:** finding ที่ใหม่หรือเกิดซ้ำกลายเป็นกฎ (ID คงที่) → เข้า checklist ที่โหลดตอนเขียน → ถ้าตรวจด้วยเครื่องได้ เสนอเป็น lint rule ของ project การเกิดซ้ำถือเป็น bug ของ workflow

## เหตุผล

- ความเสี่ยงคือสิ่งที่ทำให้งานต้องรอบคอบ ขนาดไม่ใช่ งานลบ import 50 ไฟล์เสี่ยงต่ำ งานแก้หนึ่งบรรทัดใน token validation เสี่ยงสูง
- agent ไม่ขาดความสามารถในการเขียน แต่ขาดความจำที่เชื่อถือได้และวินัยในการตรวจตัวเอง จึงย้ายสองอย่างนี้ไปไว้ในกฎที่โหลดทุกครั้งและเครื่องมือที่รันได้
- subagent มีต้นทุน (เริ่มจากศูนย์, token ซ้ำ, รายงานไม่ใช่หลักฐาน, เขียนชนกันได้) จึงใช้เมื่องานแยกได้จริงและคุ้มกว่าการ brief
